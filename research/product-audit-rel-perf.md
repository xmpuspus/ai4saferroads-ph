# Speed Safety Score — Product Audit: Reliability + Performance

Scope: `build/sss_pipeline.py`, `build/web/index.html`, `build/web/sim.html`, `tests/e2e.sh`,
`tests/check_invariants.py`, `Makefile`, `build/web/serve.py`. Live site
`https://ai4saferroads-ph.vercel.app` probed for transfer/compression. Date 2026-06-25.

Hard numbers measured this pass:
- Manila segments = **12,420** features (5.5MB raw GeoJSON), Cebu 9,064 (4.0MB), Hanoi 10,010 (4.7MB).
- Traffic animation drives **152 dots** for Manila via `setData()` every frame (top-140 flagged segments, 1-3 dots each). 944 segments flagged total.
- Live host serves GeoJSON with **brotli**: Manila 5.5MB raw -> ~519KB on the wire. Cold load (index + maplibre-gl.js + cities.json + Manila seg + Manila poi) = **~745KB on the wire**, but the browser still parses the full 5.5MB into 12,420 features.
- maplibre-gl.js loaded **blocking in `<head>`** from unpkg = 211KB wire.
- `bash tests/e2e.sh` currently **FAILS** (2 stale checks).

## Reliability assessment

What's solid: pipeline has real mirror fallback (3 Overpass endpoints), `parse_maxspeed` handles
the common junk values, `safe_speed` correctly checks grade-separated classes first (the Skyway
fix, verified by `check_invariants.py:49,56`), invariants meaningfully guard the OUTPUT methodology
(score-only-where-gap, no motorway->30, fatal-reduction present, ranges), and the live host adds a
CSP + nosniff. `prefers-reduced-motion` is honored (`index.html:106,128`).

What's weak: the **test suite is currently red** and the README claims it's green. The web layer
has **no fetch error handling at all** — a partial deploy or flaky mobile connection yields a silent
blank map. The pipeline accepts empty Overpass responses as success and doesn't retry the primary
mirror on 429. A rapid city-switch race can paint the wrong city. None of the actual code
(pipeline functions, sim physics, fetch paths, animation) is unit-tested — invariants only inspect
the last committed geojson, so a `parse_maxspeed`/`safe_speed` regression ships green until someone
re-runs `make data`.

**Reliability score: 58/100.** (Real mirror fallback + meaningful output invariants + CSP pull it
up; the red suite, zero web error handling, empty-response-as-success, and untested core code pull
it down. The worst single failure mode is the silent blank map on any fetch failure, with no retry
and no message — a user just sees a dead dark screen.)

## Performance assessment

What's solid: the live host serves GeoJSON with **brotli** (5.5MB Manila -> ~519KB on the wire), so
transfer is not the problem; cache-control is set; only 152 traffic dots animate (not thousands);
Esri default tiles are 1x. Cold load to first city ~745KB wire, sub-second on a good connection.

What's weak: the bottleneck is **client-side parse + render of 12,420 LineString features** per city
(JSON.parse of 5.5MB + tessellation on the main thread, repeated on every city switch), plus the
full grey `seg-base` underlay drawing all 12.4k segments when only ~944 are flagged. The traffic
loop replaces the entire 152-feature GeoJSON source via `setData` 60x/second with no
`visibilitychange` pause and no off-screen guard, which pegs a CPU core and drains battery on
low-end mobile. CARTO dark tiles pull `@2x` retina unconditionally (4x pixels on 1x/mobile screens).
maplibre-gl.js render-blocks in `<head>` from a third-party CDN. The build does nothing to minify or
pre-tile; it leans entirely on the host's brotli.

**Performance score: 64/100.** (Brotli + small dot count + 1x default tiles save it; the 12.4k-feature
main-thread parse/render, the full-underlay draw, the per-frame `setData` with no visibility pause,
and the unconditional `@2x` dark tiles are the real costs. The single biggest win is pre-tiling the
segments — PMTiles/vector tiles or shipping only flagged+context geometry — which removes the
multi-hundred-ms stall on every city switch.)
